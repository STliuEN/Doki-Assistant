# Benchmark 新手指南：是什么、为什么、怎么一步步上手

> 面向完全没有相关背景的人。读完你能明白 benchmark 是什么、这个项目为什么需要它，
> 以及如何从零开始、一步步把它建起来。配套的工程细节版见
> [Benchmark 开发者指南](benchmark_engineering_plan.md)，两份配合看。

## 一、先用大白话说清楚 benchmark 是什么

benchmark（基准测试）就是一套**固定的考题 + 标准答案 + 自动打分**。

打个比方：你的 AI 助手就像一个学生。你每天都在改它（改提示词、改工具、改路由逻辑）。
改完之后你怎么知道它是变聪明了还是变笨了？

- 没有 benchmark：你只能手动随便问几句，凭感觉判断“好像还行”。改一次试一次，既累又不可靠。
- 有 benchmark：你准备好 20 道固定考题，每次改完代码就让它把这 20 道题重做一遍，
  程序自动对照标准答案打分。分数涨了就是变好，跌了就是变差，一目了然。

**一句话：benchmark 就是给你的 AI 助手准备的一套“自动批改的固定试卷”。**

### 它和普通测试（单元测试）有什么区别？

- 普通单元测试问的是：“这个函数算 1+1 等于 2 吗？”——答案唯一、对错分明。
- benchmark 问的是：“让助手安排一个 30 分钟复习计划，它答得够好吗？”
  ——答案不唯一，所以我们不查“逐字对错”，而是查“关键要素在不在、该用的工具用没用、不该做的事有没有做”。

这个项目两者都需要：单元测试保函数正确，benchmark 保整体表现不退步。

## 二、为什么这个项目特别需要它

这个项目是一个 AI 助手，它的一次回答要串起很多环节：

1. 看懂你的问题，决定启用哪些技能（Skill 路由）。
2. 挑出能用的工具（比如查复习事项、读笔记）。
3. 调用大模型，一边思考一边调工具。
4. 把答案一段一段实时推给前端（这叫 SSE 流式输出）。
5. 最后把对话存进数据库。

**问题在于：这 5 个环节任何一个出小毛病，最终回答都可能变差，但你很难一眼看出是哪一环坏了。**
比如答案突然变短，可能是路由没选对工具，也可能是流式输出丢了内容，还可能是模型本身的问题。

benchmark 的价值就是：把每一环都变成可测、可打分、可定位的考题。出问题时它能告诉你
“是第几环、哪道题、错在哪”，而不是只让你看到一个模糊的“变差了”。

## 三、几个绕不开的名词（看一眼就懂）

| 名词 | 大白话解释 |
|------|-----------|
| **case（考题）** | 一道题。包含“问什么、期待什么、不能出现什么”。用 YAML 文件写，不写死在代码里。 |
| **suite（科目）** | 一组同类考题。比如 `tool_safety` 专门考“危险操作有没有被拦住”。 |
| **runner（监考程序）** | 自动把每道题丢给助手作答、收集结果的脚本。 |
| **scorer（批改程序）** | 拿助手的回答对照标准答案打分的脚本。 |
| **fixture（道具）** | 考试用的假数据。比如假的复习事项、假的笔记，保证每次考题环境一模一样。 |
| **trace（监控录像）** | 助手作答过程的逐步记录。出错时回放它，看卡在哪一步。 |
| **baseline（基准线）** | 上一次的分数存档。新分数和它一比，就知道涨了还是跌了。 |
| **offline / online（离线/在线）** | 离线=用“预先写好的假模型”，快且免费，每次提交都能跑；在线=用真模型，慢且花钱，偶尔跑。 |
| **SSE（流式输出）** | 助手答案一段段实时往外吐，而不是憋完整段才发。前端打字机效果就是它。 |
| **Skill 路由** | 助手根据你的问题，自动决定该启用哪些技能/工具的过程。 |

### 为什么要分「离线」和「在线」？

真模型每次调用要花钱、要联网、答案还每次都不一样（今天这么答、明天那么答）。
如果每次改代码都用真模型跑 20 道题，又慢又贵又不稳定。

所以我们主要用**离线模式**：事先把“模型这一轮该吐什么字、该调哪个工具、工具返回什么”
写成一个剧本文件，让程序照着剧本演。这样：

- 不花钱、不联网、几秒钟跑完。
- 每次结果完全一样，分数波动只可能来自你的代码改动，定位特别准。
- 真正测的是你的代码链路（路由、流式、工具拦截），而不是模型的脑子。

真模型质量（答得到底好不好）留给**在线模式**，手动或每晚跑一次就够了。

## 四、一道考题（case）长什么样

考题用 YAML 写，像填表格一样。下面这道题考的是“能不能根据复习事项排出 30 分钟计划”：

```yaml
id: agent_basic.review_plan_001     # 题号
title: 根据复习事项生成 30 分钟计划   # 题目描述
mode: offline                        # 用假模型跑（快、免费、稳定）

input:                               # 给助手的输入
  query: "帮我根据今天的复习事项安排一个 30 分钟计划"

fixtures:                            # 这道题用的假数据
  memories: "fixtures/memories/review_items.json"   # 假的复习事项
  model_script: "fixtures/scripts/review_plan_001.json"  # 假模型的「剧本」

expect:                              # 标准答案 / 评分标准
  must_include: ["30"]               # 回答里必须出现「30」
  must_not_include: []               # 不能出现的内容（这题没有）
  tool_policy:
    allowed: ["today_reviews"]       # 允许调用的工具
    forbidden: ["delete_memory"]     # 危险工具：可以被尝试，但绝不能真正执行
  min_score: 0.75                    # 至少考到 0.75 分才算过
```

读法：这道题给助手一句话，助手该去查复习事项（`today_reviews`），
最后给出的计划里要出现“30”。至于 `delete_memory`——它是危险操作，
**就算助手真的去调用，系统也必须在执行前把它拦下来**（这正是安全考题要验证的：
拦住了算通过，真删了才算失败）。程序照这些规则自动打分。

**关键点：考题是数据，不是代码。** 你想加新题，只要照着复制一份 YAML 改改，
不用懂编程、不用改 runner，这是整套设计最适合新手上手的地方。

## 五、整套东西是怎么跑起来的（流程图）

```
        你改了代码
             │
             ▼
   ┌──────────────────┐
   │  runner 监考程序   │  逐条读取 cases/ 下的考题
   └──────────────────┘
             │  把每道题丢给助手（离线模式用假模型剧本）
             ▼
   ┌──────────────────┐
   │   助手真实链路      │  路由→选工具→（假）模型→流式输出→落库
   │ （生产代码本身）    │  ← 注意：跑的是真代码，只有模型是假的
   └──────────────────┘
             │  产出：回答内容 + trace 监控录像
             ▼
   ┌──────────────────┐
   │  scorer 批改程序   │  对照 expect 打分：关键词、工具、安全红线
   └──────────────────┘
             │
             ▼
   ┌──────────────────┐
   │  report 报告程序   │  汇总成一张 Markdown 成绩单
   └──────────────────┘
             │
             ▼
   和上次的 baseline 比 → 分数涨了/跌了？哪道题挂了？挂在哪一步？
```

最重要的一句话：**离线模式下“假”的只有模型的大脑，路由、工具拦截、流式输出、落库
全是真代码。** 所以它测的是你真正会改坏的那些地方。

## 六、从零开始的上手计划（小白也能照着做）

按这个顺序走，每一步都小、都能立刻验证，不会一上来就被复杂度淹没。
每步给出「目标 / 你要做什么 / 怎么算成功」。

### 第 0 步：先把环境跑通（半天）

你什么都还没建，先确认现有项目能跑、现有测试能过。

- 你要做什么：
  - 打开终端，进 `backend` 目录，运行 `uv run pytest tests`，确认现有测试通过。
  - 看一眼 `backend/tests/test_agent_runtime.py` 里那个 `_FakeExecutor` 类——它就是“假模型”的雏形，后面会反复用到。
- 怎么算成功：现有测试全绿。你心里清楚“假模型”长什么样了。

> 为什么先做这步：benchmark 是盖在现有代码上的。地基不稳，上面建什么都晃。

### 第 1 步：写第一道考题（1 天）

先别管程序，先把“考什么”想清楚。

- 你要做什么：
  - 新建文件夹 `benchmarks/cases/`。
  - 照第四节的样例，手写 **1 道**最简单的考题（比如问个问题，要求回答里包含某个词）。
  - 暂时不用 `model_script`，先写最朴素的输入和 `must_include`。
- 怎么算成功：你有一个 `agent_basic.yaml`，里面一道题，自己读得懂每个字段。

> 新手建议：第一道题选“纯文字、不调工具”的，最简单。复杂的留到后面。

### 第 2 步：让一道题真的能跑（2-3 天，这步最关键）

这是从“纸上考题”到“能自动作答”的跨越，也是唯一需要写代码的硬骨头。

- 你要做什么：
  - 新建 `benchmarks/runners/run_benchmarks.py`。
  - 让它做三件事：① 读一个 YAML 考题；② 用“假模型”跑出回答；③ 把结果打印出来。
  - “假模型”怎么接？项目里 `get_agent_stream_response(...)` 有个参数 `factory`，
    默认用真模型工厂。你只要传一个**假工厂**进去，让它返回照剧本演的 `_FakeExecutor`，
    整条链路就会用假模型跑起来（详见工程版计划 B2 的“离线注入接缝”）。
- 怎么算成功：终端里运行 runner，能看到助手对你第 1 步那道题给出的回答。

> 卡住很正常：这步是整个项目技术含量最高的地方。如果自己啃不动，
> 可以让 AI 帮你照着 `_FakeExecutor` 的写法生成假工厂——这正是 AI 最擅长的活。

### 第 3 步：自动打分（1-2 天）

现在能拿到回答了，让程序替你判卷。

- 你要做什么：
  - 新建 `benchmarks/runners/score_cases.py`。
  - 先只实现最简单的两条规则：
    - `must_include` 里的词在回答里出现了吗？出现得分，没出现扣分。
    - `must_not_include` 里的词出现了吗？出现就直接判 0（安全红线）。
- 怎么算成功：跑完一道题，能打印出一个 0 到 1 之间的分数。

> 先做最笨的字符串匹配就够了。工具调用、流式合同那些高级评分，等基础跑通再加。

### 第 4 步：批量跑 + 出成绩单（1-2 天）

从“跑一道”到“跑一摞 + 一张汇总表”。

- 你要做什么：
  - 让 runner 支持一次读完 `cases/` 下所有题。
  - 新建 `report_results.py`，把所有分数汇总成一个 Markdown 表格（哪些过、哪些挂）。
  - 把考题补到 5-10 道，覆盖不同场景。
- 怎么算成功：运行一条命令，生成一个 `summary.md`，一眼看清整体表现。

### 第 5 步：存基准线，做回归对比（1 天）

让 benchmark 真正发挥“防退步”的作用。

- 你要做什么：
  - 把当前这次的成绩存成 `baselines/smoke.baseline.json`。
  - 让 report 程序在出成绩单时，顺便和基准线比一比，标出“涨了/跌了”。
- 怎么算成功：你故意改坏一点代码，再跑一次，报告能红字提示“某题分数下降”。
  ——到这一步，benchmark 就正式能用了。

### 之后可选的进阶（不急，按需做）

- 加“工具安全”考题：考危险操作有没有被拦截（项目里 `GuardedTool` 负责拦截，
  考题就验证它真的拦住了）。
- 加 trace 监控录像：出错时能回放助手卡在哪一步。
- 加前端流式测试：用 Vitest 测前端收流式数据有没有出错。
- 接真模型的在线模式：每晚自动跑一次，评估真实回答质量。

这些进阶项的工程细节，全部写在 [Benchmark 开发者指南](benchmark_engineering_plan.md)
里，那份是给“要动手实现细节”时查的。

## 七、新手常见疑问

**Q：我完全不会写代码，能做这件事吗？**
A：第 1、3、4、5 步主要是写 YAML 考题和拼装，门槛很低。
只有第 2 步（接假模型）需要真写代码，那一步可以让 AI 帮你照着现成的 `_FakeExecutor` 生成。

**Q：为什么不直接用真模型考，那样最真实？**
A：真模型慢、花钱、且每次答案不一样。你改了一行代码，分数变了，到底是你改的还是模型今天心情不同？
分不清。离线假模型保证“分数只会因你的代码改动而变”，定位问题才准。真实质量用在线模式偶尔补测。

**Q：考题答案不唯一，怎么打分？**
A：不查逐字对错，查“要素”。比如“计划里有没有出现 30 分钟”“该用的工具用了没”
“不该做的危险操作做了没”。这些都是确定的、可程序判断的。

**Q：这会不会污染我真实的数据/数据库？**
A：会，如果不隔离的话。所以考题一律用假数据（fixture），用户 ID 用 `bench-` 开头的假 ID，
数据库写入要么打桩、要么指向临时库。这点在工程版计划里有专门强调，别跳过。

**Q：要花多久才能用起来？**
A：按上面的步骤，最快第 0 到第 5 步约 1-2 周（边学边做）。
但价值是复利的——建好之后，你以后每次改代码都能省下大量手动验证的时间。

## 八、两份文档怎么配合看

- **这份（新手指南）**：搞懂“是什么、为什么、大致怎么做”。先看这份。
- **[Benchmark 开发者指南](benchmark_engineering_plan.md)**：搞懂“具体每个文件怎么写、有哪些坑”。
  真动手实现某一步时，再去查对应章节。

建议顺序：先通读这份建立全局认知 → 按第六节的步骤动手 →
每步遇到实现细节时翻开发者指南对应章节。
