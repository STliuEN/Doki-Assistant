# 下一阶段开发方案

本文基于当前 `master` 实际状态重写。项目已经不是单纯 RAG 笔记助手，而是一个具备多模型、RAG、笔记、记忆中心、实时翻译、Skill/Tool 编排和用户模型配置的个人 Agent 平台。下一阶段的重点不是继续堆页面，而是把 Agent 运行时做稳、把已有功能闭环做完整，再谨慎接入外部工具和桌面能力。

## 当前真实状态

### 已完成的基础能力

- **多模型接入**：支持工程默认模型、用户自定义 OpenAI-compatible 模型、Ollama 本地模型。
- **Agent 对话**：基于 LangChain `create_tool_calling_agent` 和 `AgentExecutor`，支持流式接口、会话持久化和模型选择。
- **Prompt / Skill / Tool 编排**：主提示词、模式提示词、Skill 指令和 Tool 描述已经分离；工具描述以 `TOOL.md` 覆盖 LangChain tool description。
- **Skill 预路由**：后端会根据用户问题，从已选 Skill 中挑选相关子集，缩小单次工具集合。
- **知识库 RAG**：支持 TXT / PDF / MD / PPTX / DOCX 上传，源文件保存，切片详情查看，Embedding 可切换，Reranker 可切换。
- **笔记系统**：支持 Markdown 编辑、搜索、统计、关联推荐、创建笔记、AI 写作辅助、自动标签分类。
- **记忆中心**：已从单纯复习扩展为 review / todo / reminder / long_term / memo，支持创建、查询、更新、完成、延期、归档、删除和复习题生成。
- **实时翻译**：已有双向实时翻译和整篇翻译模式，可使用模型配置。
- **管理页面**：前端已有模型选择、Skill 管理、Tool 管理、知识库、笔记、记忆中心等页面。

### 仍然明显不足的地方

- Agent 运行时不够可观察：普通工具调用只写后端日志，前端 thinking 折叠区不能稳定展示完整执行过程。
- 最终回答仍偏“Agent 执行完后再切块发送”，不是完整的模型/工具事件流。
- 会话历史没有自动压缩，长会话会无限堆入 `chat_history`。
- `max_iterations` 已提高到 64，但缺少运行预算、wall-clock 超时、工具调用次数限制和停止原因展示。
- 删除、外部写入等高风险动作还缺少真正的确认机制。
- 记忆中心已经可用，但主动提醒、从对话自动提炼事项、桌面通知还没有闭环。
- MCP、系统字幕、桌面端目前仍是规划，不应排在运行时稳定性之前。

## 下一阶段总原则

1. **先稳运行时，再扩工具生态**：Agent 能清楚展示自己做了什么、花了多久、为什么停止之后，再接更多外部工具。
2. **先补闭环，再做新页面**：记忆中心、笔记、知识库已有基础功能，下一步优先补自动化、状态闭环和可解释性。
3. **先本地可控，再高风险能力**：删除、文件系统、浏览器、Shell、数据库等工具必须有权限和确认机制。
4. **先个人助手体验，再平台化扩张**：当前更适合打磨个人 AI 工作台，而不是过早做团队化、多租户和复杂后台。

## P0：Agent 运行时体验升级

这是下一阶段最高优先级。它是 MCP、自动事项提炼、系统字幕沉淀和桌面长期运行的前置基础。

### P0.1 执行过程事件化

当前情况：

- `/chat/agent/query/stream` 已经走 SSE。
- 前端 `useSSE.ts` 支持 `thinking / response / done / error`。
- 前端 `AIChat.tsx` 有 thinking 折叠区。
- RAG 内部会通过 callback 推送部分 thinking。
- 普通工具调用只在 `AgentExecutor.astream()` 的 `intermediate_steps` 中被后端日志记录，没有推给前端。

目标：

- 后端推送统一事件：
  - `agent_start`
  - `tool_start`
  - `tool_end`
  - `tool_error`
  - `agent_end`
- 每个事件包含：
  - `run_id`
  - `stage`
  - `tool`
  - `input_preview`
  - `output_preview`
  - `started_at`
  - `ended_at`
  - `duration_ms`
  - `error`
- 前端 thinking 折叠区从“单条文本”改为“事件列表”，显示步骤状态和耗时。

验收标准：

- 用户能看到 Agent 调用了哪个工具、传了什么摘要、返回了什么摘要、耗时多久。
- RAG、笔记搜索、记忆事项查询、复习题生成都能展示清晰过程。
- 工具失败时前端能看到失败步骤，而不是只得到最终错误。

### P0.2 上下文自动压缩

当前情况：

- `chat_sessions` / `chat_messages` 已保存会话历史。
- `ChatSession.metadata_` 和 `ChatMessage.metadata_` 已有 JSON 字段。
- `DatabaseSessionManager.get_history()` 当前返回完整历史。
- `agent.py` 会把完整历史转为 `HumanMessage` / `AIMessage` 后塞进 Agent。

目标：

- 增加“长期摘要 + 最近窗口”的上下文结构：

```text
system prompt
  -> conversation_summary
  -> recent_messages
  -> current_user_input
  -> agent_scratchpad
```

- 在 `ChatSession.metadata_` 中保存：
  - `summary`
  - `summary_message_id`
  - `summary_updated_at`
  - `estimated_tokens`
- 超过阈值后自动压缩早期消息，例如保留最近 6 轮原文，早期内容写入摘要。

验收标准：

- 长会话不会无限增长 prompt。
- 摘要保留用户目标、偏好、长期任务和重要约束。
- 涉及知识库、笔记、记忆事项的事实仍通过工具实时检索，不依赖摘要硬答。

### P0.3 长任务预算和取消

当前情况：

- `AgentExecutor.max_iterations` 已设为 64。
- 每次请求都会创建新的 AgentExecutor，避免全局状态污染。
- 前端 `useSSE` 已有 `AbortController`，但 UI 层还没有完整停止/状态展示。

目标：

- 引入 `RunBudget`：
  - `max_iterations`
  - `max_tool_calls`
  - `max_runtime_seconds`
  - `max_output_chars_per_tool`
- SSE 展示：
  - 已运行时长
  - 已调用工具次数
  - 停止原因
- 前端提供停止按钮。
- 达到预算时生成收束回答，说明已完成步骤和未完成部分。

验收标准：

- Agent 可以稳定执行多步工具任务。
- 长任务不会无限跑。
- 用户可以中断，并看到中断前已经完成的步骤。

### P0.4 高风险操作确认

当前高风险工具包括：

- `delete_memory_tool`
- 后续 MCP 文件系统、数据库、浏览器、Shell 类工具
- 未来可能的批量删除、清库、外部写入工具

目标：

- 给 Tool 增加风险等级或权限标签。
- 高风险工具调用前进入 `waiting_confirmation` 状态。
- 前端展示操作摘要，用户确认后才继续。

验收标准：

- 删除类操作不会只靠 prompt 约束。
- Agent 能暂停等待用户确认。
- 用户拒绝后 Agent 能继续给出替代建议。

详细拆解见 [Agent 运行时改进评估](./agent_runtime_improvements.md)。

## P1：记忆中心闭环

记忆中心已经具备基础 CRUD 和 Agent 工具，但还需要从“能管理”升级为“真的能提醒和沉淀”。

### P1.1 记忆中心产品收敛

当前前端已把筛选收敛为：

- 今日
- 进行中
- 复习
- 事项
- 备忘
- 已完成

下一步：

- 继续保持 UI 聚合，不再把底层类型全部平铺给用户。
- 列表中强化状态、时间、优先级和下一步动作。
- 对 review 类型突出“今日复习 / 出题 / 已复习”。
- 对 todo / reminder / long_term / memo 统一为“事项与备忘”体验。

### P1.2 从对话自动提炼事项

当前情况：

- 用户明确说“提醒我 / 记一下 / 加待办”时，Agent 可以创建记忆事项。
- 还没有自动从普通对话、翻译结果、知识库问答中提炼事项。

目标：

- 在对话结束后可选触发事项提炼。
- 提炼结果先展示给用户确认，不自动写入。
- 支持从以下来源提炼：
  - 对话内容
  - 笔记内容
  - 翻译后的会议记录
  - 知识库问答结果

验收标准：

- 用户完成一次对话后，可以看到“可保存为待办/提醒/长期事项”的建议。
- 用户确认后才写入记忆中心。

### P1.3 主动提醒与桌面通知预备

当前情况：

- 后端能查今日事项和复习事项。
- 还没有主动提醒调度器和系统通知。

目标：

- 增加轻量 reminder scan job。
- 支持前端轮询或 WebSocket/SSE 接收提醒。
- 为后续桌面端系统通知预留接口。

验收标准：

- 到期事项能在页面内被主动提示。
- 提醒被查看、延期、完成后状态正确闭环。

## P2：Skill/Tool 体系继续收敛

当前 Skill/Tool 已经可扫描、可编辑、可选择，并且引入了 skill 预路由。下一步重点不是增加更多工具，而是让工具体系更安全、更可测试。

### P2.1 Skill 选择逻辑可解释

当前情况：

- `intent_router.py` 会先规则匹配，再 LLM 兜底。
- 路由结果当前主要写日志，前端不可见。

目标：

- 将 skill 预路由结果作为 thinking 事件展示：
  - 候选 skill
  - 命中的规则或 LLM 选择
  - 最终启用工具列表

验收标准：

- 用户或开发者能知道为什么本次只启用了某些 skill。
- 工具不可用时能判断是用户未选择、预路由过滤，还是 registry 缺失。

### P2.2 Tool 元数据完善

目标：

- `tool.yaml` 增加：
  - `risk_level`
  - `requires_confirmation`
  - `timeout_seconds`
  - `max_output_chars`
- `TOOL.md` 继续作为模型可见描述来源。

验收标准：

- 前端工具库能展示风险等级。
- Agent 运行时能根据元数据做预算和确认。

### P2.3 Tool 测试与诊断

目标：

- 每个工具提供最小 smoke test。
- 工具管理页支持测试调用。
- 失败时返回结构化错误：认证、参数、权限、外部服务、内部异常。

验收标准：

- 新增工具前可以本地验证。
- Agent 调错工具时有可诊断日志和前端事件。

## P3：MCP 外部工具接入

MCP 不应早于 P0，因为外部工具会显著增加误操作风险。等运行时事件、预算、确认机制具备后，再接入 MCP。

### 第一阶段：工具发现

- 配置一个本地 MCP server。
- 后端发现 MCP tools。
- 工具库页面展示 MCP 工具来源、名称、描述、参数。

### 第二阶段：工具适配

- MCP tool 转成项目内部统一 ToolDefinition。
- Skill 可以绑定 MCP tool。
- Agent 可以调用 MCP tool。

### 第三阶段：安全控制

- MCP server 启用/停用。
- MCP tool 启用/停用。
- 高风险工具确认。
- 调用超时和最大输出限制。

验收标准：

- 本地工具链路不受影响。
- MCP 工具可选择、可禁用、可观察。
- 文件系统、Shell、数据库类工具默认不自动开放。

## P4：实时翻译升级为字幕/会议助手

当前实时翻译已有基础页面和模型调用能力。下一步目标是接入连续文本流，而不是继续停留在手动输入。

### P4.1 字幕文本源调研

优先级：

1. Windows 系统字幕可读性调研。
2. 剪贴板 / OCR / 本地转写文件流作为替代方案。
3. 后续再考虑自研语音识别。

### P4.2 连续字幕翻译

目标：

- 按字幕片段增量翻译。
- 原文和译文逐句对齐。
- 保留最近上下文，减少术语漂移。

### P4.3 会议内容沉淀

目标：

- 翻译结束后保存为笔记。
- 自动提炼摘要、待办、术语表。
- 可写入记忆中心，进入提醒或长期事项。

## P5：桌面端可行性验证

桌面端不应过早启动完整迁移。应先验证“当前 Web 架构能否以本地服务方式稳定运行”。

### 验证目标

- 一键启动后端、前端、用户服务和依赖。
- 本地模型 Ollama 使用体验稳定。
- 本地文件访问、系统通知、字幕文本源有可行方案。
- 数据库/Redis/Chroma 是否可以简化。

### 可能路线

#### 路线 A：继续 Web 平台

适合保留多用户、远程访问、完整工程展示。

#### 路线 B：桌面端个人助手

适合本地长期运行、系统通知、本地文件和本地模型。

当前建议：

- 短期继续 Web 平台。
- 中期做桌面端最小可行性验证。
- 不急于删除 Django 用户服务、Redis 或 MySQL，先观察个人使用场景是否真的需要精简。

## 推荐执行顺序

1. **P0 Agent 运行时体验升级**
   - 执行过程事件化
   - thinking 折叠区事件列表
   - 上下文压缩
   - 运行预算与取消
   - 高风险操作确认

2. **P1 记忆中心闭环**
   - 事项提炼
   - 主动提醒
   - 页面交互继续收敛

3. **P2 Skill/Tool 体系收敛**
   - skill 预路由可解释
   - tool 风险元数据
   - 工具测试与诊断

4. **P3 MCP 接入**
   - 先发现
   - 再适配
   - 最后开放高风险能力

5. **P4 实时翻译字幕化**
   - 接文本流
   - 做增量翻译
   - 沉淀会议记录

6. **P5 桌面端验证**
   - 验证本地运行和系统能力
   - 再决定是否精简架构

## 暂不优先的事项

- 不优先做团队协作和多租户管理。
- 不优先做复杂工作流编排器。
- 不优先完全迁移 LangGraph，先用现有 `AgentExecutor` 做事件化和预算控制。
- 不优先重写前后端架构。
- 不优先引入大量外部工具，先把现有工具调用做可观察、可控、可诊断。

## 最终目标

Doki Assistant 的下一阶段目标是成为一个长期在线的个人 AI 工作台：

- 能理解用户资料和笔记。
- 能记住并提醒用户的事项。
- 能清楚展示自己调用了哪些工具。
- 能长时间执行任务但不失控。
- 能逐步接入外部工具和系统能力。

路线图的重点不是“功能更多”，而是“执行更稳、过程可见、风险可控、日常可用”。
