# 下一阶段开发路线图

当前项目已经从单纯的 RAG 笔记助手演进为多模型 Agent 平台。下一阶段不再继续堆单点功能，而是围绕“更像日常可用的个人 AI 助手”重构产品形态：让它能记事、提醒、翻译、调用外部工具，并在更轻量的桌面环境里长期运行。

## 方向一：从回顾系统升级为智能备忘录

现在的回顾系统主要服务于笔记复习，核心是“到时间提醒用户回看笔记”。下一步要把它升级成更通用的智能备忘录，让系统不只记住知识，也能记住待办、承诺、临时想法、会议事项和长期目标。

### 为什么要做

- 真实使用中，用户需要被提醒的不只有学习笔记，还有“某天要做什么”“某件事还没处理”“某个想法值得以后继续推进”。
- 单纯的间隔重复更像学习工具，智能备忘录更接近日常 AI 助手。
- Agent 已经具备笔记检索和创建能力，下一步自然可以让它从对话中提炼备忘事项。

### 规划方法

- **统一记忆对象**：把笔记、回顾、待办、提醒、长期事项看成不同类型的个人记忆，而不是完全分散的功能。
- **智能提炼**：支持从对话、笔记、翻译记录和知识库问答中提取可执行事项。
- **主动提醒**：不只按固定复习间隔提醒，也可以按日期、优先级、上下文和未完成状态提醒。
- **状态闭环**：每条备忘录应该能经历创建、提醒、延期、完成、归档，而不是只被动展示。
- **与 Agent 联动**：用户可以直接对 Agent 说“提醒我”“帮我整理今天待办”“这件事下周再看”，系统自动生成备忘。

### 阶段目标

1. 把“每日回顾”产品概念调整为“智能备忘录 / 记忆中心”。
2. 保留原有笔记复习能力，作为备忘录的一种类型。
3. 增加待办、提醒、长期事项等类型。
4. 让 Agent 可以创建和查询备忘事项。
5. 后续再加入从对话中自动提炼备忘录的能力。

## 方向二：MCP 支持

MCP 的目标是让项目从“只能调用自己写好的工具”升级为“可以接入外部工具生态”。它不替代现有 Skill/Tool，而是成为外部工具适配层。

### 为什么要做

- 当前工具系统已经模块化，但新增外部工具仍需要手写适配。
- MCP 可以让文件系统、数据库、浏览器、第三方平台等能力通过统一协议接入。
- 这会把项目从“内置工具平台”升级为“可连接外部世界的 Agent 工作台”。

### 规划方法

- **不破坏现有 Skill/Tool**：本地工具继续保留，MCP 作为新的工具来源加入。
- **先工具，后资源**：第一阶段只做工具发现和工具调用，先不展开资源、提示词、采样、远程鉴权等完整能力。
- **统一注册层**：本地工具和 MCP 工具都进入同一个工具注册层，再交给 Skill 绑定。
- **前端可管理**：用户可以启用或停用 MCP 服务，查看服务提供的工具，并决定哪些工具允许被 Agent 调用。
- **安全优先**：文件系统、浏览器、数据库、Shell 类工具必须有权限开关、调用日志和高风险操作确认。

### 阶段目标

1. 支持配置一个本地 MCP 服务。
2. 能发现 MCP 服务暴露的工具。
3. 工具库页面能展示 MCP 工具。
4. Skill 可以绑定 MCP 工具。
5. Agent 能在对话中调用 MCP 工具。
6. 默认本地工具链路保持不变。

## 方向三：实时翻译接入系统字幕

当前实时翻译已经支持双语对话和整篇翻译，但它仍然依赖用户手动输入。下一步希望同步微软系统字幕或系统级语音转写，让它接近真正的实时对话翻译。

### 为什么要做

- 手动输入只适合短句测试，不适合会议、网课、语音通话或现场对话。
- Windows 系统字幕已经能把麦克风或系统声音转成实时文本，如果能接入这类文本流，就可以把翻译页面变成真正的实时字幕翻译器。
- 这会让实时翻译从“翻译工具”升级为“实时沟通辅助”。

### 规划方法

- **先接文本流**：优先寻找系统字幕、剪贴板、OCR 或本地转写结果的文本接入方式，而不是一开始就自研语音识别。
- **保持双栏对齐**：实时字幕会不断追加内容，界面必须保持原文和译文逐句对齐。
- **增量翻译**：按短句或字幕片段翻译，避免每次重翻整段内容。
- **上下文修正**：保留最近若干句上下文，减少代词、术语和语气翻译错误。
- **会议记录沉淀**：翻译结束后可以保存为笔记，并自动提炼摘要、待办和术语表。

### 阶段目标

1. 调研 Windows 系统字幕或微软字幕文本是否能稳定读取。
2. 增加一个“字幕输入源”概念，和手动输入并存。
3. 支持连续字幕流进入翻译队列。
4. 保持原文和译文逐句同步对齐。
5. 翻译结果可保存为笔记，并进入后续备忘录/知识库流程。

## 方向四：精简架构，走向桌面端日常 AI 助手

当前项目采用前后端分离、独立用户服务、数据库、Redis、Chroma 等完整 Web 架构，适合展示工程能力，但对个人日常使用来说启动和部署偏重。下一步需要判断产品形态：继续做 Web Agent 平台，还是精简为桌面端日常 AI 助手。

### 为什么要做

- 个人使用更看重低摩擦启动、稳定运行和本地模型接入，而不是复杂部署。
- 桌面端更适合接系统字幕、剪贴板、文件系统、本地模型和系统级通知。
- 如果目标是“日常 AI 助手”，架构应该服务于使用频率，而不是保留所有演示型组件。

### 规划方法

- **保留核心能力**：多模型调用、Agent 对话、RAG 知识库、实时翻译、智能备忘录是核心。
- **弱化重型服务**：评估是否移除或合并独立用户服务、Redis、复杂鉴权和多用户隔离。
- **本地优先**：优先支持 Ollama、本地文件、本地数据库和本地向量索引。
- **桌面壳承载**：评估 Tauri 或 Electron，把现有前端作为桌面 UI，后端以本地服务或内嵌进程运行。
- **多 AI 调用中枢**：把模型选择从单个页面升级为统一调用中枢，让聊天、翻译、总结、备忘录都能选择合适模型。

### 两条可能路线

#### 路线 A：继续 Web 平台化

适合保留完整工程展示、多用户、服务端部署和远程访问能力。优点是架构完整，适合扩展成团队知识平台；缺点是个人使用成本高。

#### 路线 B：桌面端个人助手

适合本地长期使用、调用系统能力、接入本地模型和系统字幕。优点是实用性强，用户体验更自然；缺点是需要重新梳理后端依赖和打包方式。

当前更推荐先做“桌面端可行性验证”：不急着完全迁移，而是先验证本地启动、系统字幕接入、本地文件访问和模型调用体验。如果桌面端体验明显更好，再逐步精简架构。

## 推荐执行顺序

1. **智能备忘录**：先把产品定位从笔记复习扩展到日常记忆和提醒，这是最直接提升实用性的方向。
2. **MCP 支持**：在 Tool Registry 已经模块化的基础上接外部工具，扩大 Agent 能力边界。
3. **实时翻译接系统字幕**：把已有翻译页升级为真正可用于会议和对话的实时字幕翻译。
4. **桌面端可行性验证**：等核心场景更清楚后，再决定是否精简架构并迁移到桌面端。

这四个方向应该互相支撑：智能备忘录负责“记住事情”，MCP 负责“连接工具”，实时翻译负责“接住现场信息”，桌面端负责“降低日常使用摩擦”。最终目标不是做更多页面，而是让 Doki Assistant 变成一个长期在线、能理解资料和任务、能调用外部工具的个人 AI 助手。
