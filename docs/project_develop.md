## 项目变迁

### 阶段一：基础 RAG 对话系统

最初是一个**纯粹的技术演示**——用 FastAPI + LangChain + ChromaDB 搭建了一套完整的 RAG 对话链路：文档上传 → 切片 → 向量化 → 检索 → LLM 生成。功能简单但技术栈完整，适合作为 RAG 入门的参考实现。

**转型的契机：** 这个版本虽然能跑通 RAG 全流程，但解决的需求太泛——"基于文档问答"，没有固定的使用场景。所以无法写进简历，无法作为求职项目，缺乏"解决具体痛点"的说服力。

### 阶段二：RAG NoteBook 智能笔记助手

在 RAG 实践中发现一个更普遍的痛点——**笔记写了从不回看，知识散落成孤岛**。于是围绕这个场景，在 RAG 引擎之上做了几件事：

- **笔记管理**：Markdown 编辑器、LLM 自动标签分类、语义搜索
- **间隔重复回顾**：艾宾浩斯遗忘曲线，到点提醒回顾，对抗遗忘
- **AI 写作辅助**：联机补全、续写扩写、跨源关联推荐
- **Agent 工具集成**：对话中直接搜索笔记、创建笔记、查看回顾
- **智能问答**：RAG同时检索笔记库和知识库，做完笔记就可以直接同步到笔记库，越用越聪明

**RAG 始终是核心引擎。** 无论是笔记语义搜索、关联推荐还是对话检索，底层都是同一套向量检索链路。

### 阶段三：升级为多功能智能 Agent 平台

随着项目继续演进，系统已经不只是一个“会查笔记的 RAG 助手”，而是逐步增加了多模型接入、AI 对话模式、实时翻译、笔记保存、模型选择等更完整的使用流程。当前阶段的目标，是把它升级成一个**多功能智能 Agent 平台**：让用户可以按任务组合模型、提示词、技能和外部工具，而不是只能使用固定写死的对话链路。

这一阶段重点引入几类平台能力：

- **多模型运行时**：支持默认配置、Ollama 本地模型、OpenAI 兼容模型，并允许不同页面和不同任务选择不同模型
- **Prompt Composer**：组合主提示词、角色模式提示词、技能提示词和用户临时指令，让 Agent 的行为可以按场景切换
- **Skill Registry**：把写作、翻译、笔记整理、资料检索、代码辅助等能力注册成可选择、可扩展的技能
- **Tool Registry**：统一管理内置工具、笔记工具、知识库检索工具、HTTP 外部工具，后续可以扩展到 MCP、浏览器、文件系统等工具类型
- **用户自定义能力**：允许用户添加自己的技能说明、工具配置和调用参数，让系统从“预设应用”变成“可配置工作台”
- **任务工作流编排**：围绕真实使用场景组织能力，例如实时双语对话、学习笔记整理、资料问答、自动归档、复习计划生成

**这一阶段的核心变化是：** RAG 不再只是单独的问答功能，而是作为 Agent 的长期记忆和知识底座存在；Agent 负责根据用户任务选择合适的模型、提示词、技能和工具，把项目从“智能笔记助手”升级为可以持续扩展的个人 AI 工作平台。

#### 当前已完成的模块化改造

第一步已经把原先写在 Agent 代码里的固定能力拆成了接近 Codex 风格的独立模块：

- **Skill 独立模块**：`backend/app/agent/skills/<skill_id>/skill.yaml` 负责元数据和绑定工具，`SKILL.md` 负责能力说明。当前默认包含系统上下文、知识库问答、笔记检索、笔记写入、复习回顾 5 个 Skill。
- **Tool 独立模块**：`backend/app/agent/tools/<tool_id>/tool.yaml` 负责元数据，`TOOL.md` 负责工具说明，`tool.py` 暴露 `get_tool()` 返回 LangChain `BaseTool`。当前默认包含 RAG 总结、当前时间、用户信息、笔记搜索、笔记统计、今日回顾、标记回顾、创建笔记、关联推荐 9 个 Tool。
- **默认链路兼容**：前端没有显式修改 Skill/Tool 选择时，请求不发送 `skill_ids/tool_ids`，后端默认启用全部默认 Skill，并解析出原始 9 个 Tool，保证初版 Agent 行为不回退。
- **前端配置入口**：AI 对话页支持 Skill 下拉勾选，左侧导航新增 `Skill` 与 `工具库` 页面，支持查看、编辑、新增、删除模块文件。Skill 绑定工具已经改为按工具分类展开的二级菜单，避免工具数量增加后撑开页面。
- **新建状态修复**：Skill 和 Tool 新建时使用独立的新建状态，不再被列表自动选中第一项覆盖；Skill 详情加载也加入失效保护，避免旧请求晚返回覆盖新建草稿。

#### 当前执行链路

```text
前端 AI 对话
  -> 选择模型、Prompt 模式、Skill 勾选状态
  -> POST /chat/agent/query/stream
  -> resolve_skills(skill_ids, tool_ids)
  -> Skill Registry 读取启用 Skill 的 SKILL.md
  -> Tool Registry 加载绑定 Tool 的 tool.py:get_tool()
  -> 拼接主 Prompt、模式 Prompt、Skill 指令
  -> 注入 LangChain BaseTool
  -> AgentExecutor 执行并流式返回
```

当前新增 Skill/Tool 会生成同样结构的可用文件模块；Tool 新增时会生成占位 `tool.py`，后续可以继续把占位工具升级为 HTTP、MCP、数据库查询、浏览器或文件系统等具体工具模板。

#### RAG 基座稳定性更新

在知识库与笔记索引改为“源文件入库、向量库可重建”之后，RAG 的稳定性重点转向模型加载和可恢复执行。本轮补齐了重排序模型的加载保护：

- `ReorderService` 不再只判断模型目录是否存在，而是校验 `config.json` 和权重文件是否完整。
- ModelScope 下载中断留下的 `._____temp`、`.lock` 不再被误判为可用模型。
- 后台初始化会真实预热 CrossEncoder，提前暴露本地模型缺失或依赖不兼容问题。
- 如果 reranker 加载失败，RAG 会跳过重排序并保留原始检索结果，避免增强层失败拖垮知识库问答。
- 对 RTX 50 系列 `sm_120` 显卡，当前 `torch + cu126` 不支持 GPU 推理时会自动回退 CPU；如需 GPU 重排序，后续应重建后端 `.venv` 并升级到 CUDA 13.x PyTorch 构建。

这次改动没有改变 RAG 的业务链路：检索仍然先从用户隔离的知识库与笔记向量集合取候选，再交由 reranker 排序，最后进入 LLM 总结。变化在于 reranker 从“启动后第一次调用才暴露问题”变为“启动期预热、失败可降级、日志可诊断”。

### base-rag 分支

考虑有学习基础RAG的需要，我们将阶段一的代码永久保留为 `base-rag` 分支，与 master 独立演进，保持最小可运行状态。需要纯 RAG 服务或学习 RAG 技术的同学，切换过去即可。后续base-rag也会继续维护

### 结语

RAG NoteBook 的目标是成为**真正能用的个人知识管理工具**，而不仅仅是又一个 AI demo。后续也会继续维护`master`和`base-rag`分支。如有问题或建议，欢迎在Issues里提问。
