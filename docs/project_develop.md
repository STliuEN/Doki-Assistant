## 项目变迁

### 阶段一：基础 RAG 对话系统

最初是一个**纯粹的技术演示**——用 FastAPI + LangChain + ChromaDB 搭建了一套完整的 RAG 对话链路：文档上传 → 切片 → 向量化 → 检索 → LLM 生成。功能简单但技术栈完整，适合作为 RAG 入门的参考实现。

**转型的契机：** 这个版本虽然能跑通 RAG 全流程，但解决的需求太泛——"基于文档问答"，没有固定的使用场景。所以无法写进简历，无法作为求职项目，缺乏"解决具体痛点"的说服力。

### 阶段二：RAG NoteBook 智能笔记助手

在 RAG 实践中发现一个更普遍的痛点——**笔记写了从不回看，知识散落成孤岛**。于是围绕这个场景，在 RAG 引擎之上做了几件事：

- **笔记管理**：Markdown 编辑器、LLM 自动标签分类、语义搜索
- **间隔重复回顾**：艾宾浩斯遗忘曲线，到点提醒回顾，对抗遗忘
- **AI 写作辅助**：联机补全、续写扩写、跨源关联推荐
- **Agent 工具集成**：对话中直接搜索笔记、创建笔记、查看回顾
- **智能问答**：RAG同时检索笔记库和知识库，做完笔记就可以直接同步到笔记库，越用越聪明

**RAG 始终是核心引擎。** 无论是笔记语义搜索、关联推荐还是对话检索，底层都是同一套向量检索链路。

### 阶段三：升级为多功能智能 Agent 平台

随着项目继续演进，系统已经不只是一个“会查笔记的 RAG 助手”，而是逐步增加了多模型接入、AI 对话模式、实时翻译、笔记保存、模型选择等更完整的使用流程。当前阶段的目标，是把它升级成一个**多功能智能 Agent 平台**：让用户可以按任务组合模型、提示词、技能和外部工具，而不是只能使用固定写死的对话链路。

这一阶段重点引入几类平台能力：

- **多模型运行时**：支持默认配置、Ollama 本地模型、OpenAI 兼容模型，并允许不同页面和不同任务选择不同模型
- **Prompt Composer**：组合主提示词、角色模式提示词、技能提示词和用户临时指令，让 Agent 的行为可以按场景切换
- **Skill Registry**：把写作、翻译、笔记整理、资料检索、代码辅助等能力注册成可选择、可扩展的技能
- **Tool Registry**：统一管理内置工具、笔记工具、知识库检索工具、HTTP 外部工具，后续可以扩展到 MCP、浏览器、文件系统等工具类型
- **用户自定义能力**：允许用户添加自己的技能说明、工具配置和调用参数，让系统从“预设应用”变成“可配置工作台”
- **任务工作流编排**：围绕真实使用场景组织能力，例如实时双语对话、学习笔记整理、资料问答、自动归档、复习计划生成

**这一阶段的核心变化是：** RAG 不再只是单独的问答功能，而是作为 Agent 的长期记忆和知识底座存在；Agent 负责根据用户任务选择合适的模型、提示词、技能和工具，把项目从“智能笔记助手”升级为可以持续扩展的个人 AI 工作平台。

#### 当前已完成的模块化改造

第一步是把原先写在 Agent 代码里的固定能力拆成接近 Codex 风格的独立能力包。每个 Skill 只描述“这个能力应该如何工作”，每个 Tool 只负责“可以执行什么动作”，Agent 在运行时再根据选择结果把它们组合起来。

采用这种方式后，系统得到几个关键收益：

- **能力解耦**：知识库问答、笔记检索、笔记写入、复习回顾等能力不再散落在 Agent 主流程里，而是变成可独立查看和维护的 Skill。
- **工具解耦**：RAG 检索、当前时间、用户信息、笔记搜索、创建笔记等动作从集中式工具列表中拆出，变成可注册、可选择、可扩展的 Tool。
- **默认体验不变**：默认情况下仍然启用完整能力集合，保证早期版本能跑通的 Agent 链路不会因为模块化而退化。
- **前端可配置**：AI 对话页可以按任务勾选 Skill，管理页可以查看、编辑、新增和删除 Skill/Tool，让系统从“固定应用”变成“可配置工作台”。
- **扩展路径明确**：后续无论加入 HTTP 工具、数据库工具、浏览器工具还是 MCP 工具，都可以沿用同一套注册和选择机制。

当前 Agent 的执行方式可以概括为：用户选择模型、模式和 Skill 后，后端把主提示词、模式提示词和 Skill 指令组合起来，再把这些 Skill 绑定的工具注入 Agent，由 Agent 自主决定何时调用工具并流式返回结果。

#### 下一步优先级：Agent 运行时体验

Skill/Tool 模块化完成后，下一步优先级不是继续堆更多工具，而是先把 Agent 运行时做得更稳定、更可观察。当前运行时已经具备数据库会话历史、SSE 通道、工具上下文和较高的迭代上限，但仍需要补齐三项基础能力：

- **执行过程流式事件**：把模型调用、工具调用、工具结果、错误和耗时推送到前端 thinking 折叠区，而不是只在后端日志里可见。
- **上下文自动压缩**：把早期会话压缩为摘要，只保留最近若干轮原文，降低长对话成本和溢出风险。
- **长任务预算控制**：支持更多轮工具调用，同时提供运行时长、工具调用次数、取消、超时和高风险操作确认。

这部分是 MCP、自动事项提炼、系统字幕翻译沉淀和桌面端长期运行的前置基础。详细评估与实施顺序见 [Agent 运行时改进评估](./agent_runtime_improvements.md)。

#### RAG 基座稳定性更新

在知识库与笔记索引改为“源文件入库、向量库可重建”之后，RAG 的稳定性重点转向模型加载和可恢复执行。本轮补齐了重排序模型的加载保护：

- **完整性校验**：不再只看模型目录是否存在，而是检查模型配置和权重是否完整，避免把中断下载的目录当成可用模型。
- **启动期诊断**：在后台初始化阶段提前验证重排序模型是否能加载，尽早暴露模型缺失、依赖不兼容或显卡架构不支持的问题。
- **失败可降级**：重排序只是检索增强层，失败时不应该拖垮整个知识库问答，因此系统会保留原始检索结果继续回答。
- **本地算力适配**：为 RTX 50 系列这类新显卡准备了更新的 PyTorch/CUDA 依赖方案，让 4B 重排序模型能优先使用 GPU；不满足条件时也能回退 CPU。
- **推理参数可调**：把长上下文、批大小和精度等影响显存与速度的参数开放出来，便于在轻量模型和 4B 模型之间切换。

这次改动没有改变 RAG 的业务链路：检索仍然先从用户隔离的知识库与笔记向量集合取候选，再交由 reranker 排序，最后进入 LLM 总结。变化在于 reranker 从“启动后第一次调用才暴露问题”变为“启动期预热、失败可降级、日志可诊断”。

#### 知识库模型配置与可追溯索引

知识库管理已经从“只管理 Chroma 向量”调整为“源文件与配置可追溯，向量索引可重建”的结构：

- 上传文件会先保存源文件和元数据，再进入解析、切片和向量化流程；这样向量库损坏或 embedding 模型切换后，可以从源文件重新构建索引。
- 文件导入采用队列化处理和实时进度反馈，前端可以看到每个文件的处理状态和失败原因。
- 文档解析范围扩展到 TXT / PDF / MD / PPTX / DOCX。
- Embedding 配置按用户保存，切换 embedding 后会重建当前用户的知识库索引和笔记索引，保证同一批向量来自同一个 embedding 空间。
- Reranker 作为召回后的排序增强层独立配置，可以在轻量模型和更强的 4B 模型之间切换。
- Reranker 切换不会重建向量库，因为它只作用在候选片段排序阶段，不改变向量索引本身。

当前 RAG 数据链路可以概括为：

```text
上传文件
  -> 保存源文件和元数据
  -> 解析并切片
  -> 使用当前 embedding 写入向量索引
  -> 查询时召回知识库和笔记候选
  -> 使用当前 reranker 重排候选
  -> 拼接上下文交给 LLM
```

#### 下一阶段：MCP 外部工具协议层

当前 Skill/Tool 已经完成文件模块化，RAG 也具备源文件可追溯和模型可切换能力。下一步适合引入 MCP（Model Context Protocol），把外部工具接入从“项目内手写适配”升级为“通过协议发现和调用外部工具”。

MCP 在当前项目中的定位不是替代 Skill/Tool，而是作为外部工具适配层。项目内部继续用 Skill 描述任务能力，用 Tool 描述可执行动作；MCP 负责把文件系统、数据库、浏览器、第三方平台等外部能力以统一协议接进来。

```text
本地工具
  -> 项目内置能力

MCP 工具
  -> 外部系统能力

统一工具注册层
  -> 合并两类工具
  -> 继续交给 Skill 绑定和 Agent 调用
```

规划方法：

- **先接工具，不急着接全部协议能力**：第一阶段只接 MCP 的工具发现和工具调用，资源、提示词、采样、远程鉴权等能力后置。
- **先做适配层，再做复杂工作流**：MCP 工具先统一转成项目现有 Agent 能理解的工具形式，避免打断当前 Skill/Tool 选择链路。
- **本地工具和外部工具并存**：默认能力继续来自本地工具，MCP 作为额外工具来源加入，保证旧链路不受影响。
- **前端只暴露必要控制**：先支持服务器启用、连接测试、工具刷新、工具开关和工具信息查看，避免一开始把 MCP 复杂度全部压给用户。
- **Skill 仍然是组织入口**：用户不直接面对一长串外部工具，而是通过 Skill 把工具组合成可理解的任务能力。

第一阶段最小验收目标是：

```text
配置一个 MCP 服务
  -> 系统能发现它提供的工具
  -> 前端能展示这些工具
  -> Skill 可以绑定这些工具
  -> Agent 可以在对话中调用这些工具
  -> 默认本地能力链路保持不变
```

MCP 引入后必须同步补权限控制：server 启用开关、tool 启用开关、调用超时、最大返回长度、危险工具二次确认和工具调用日志。尤其是文件系统、数据库、浏览器、Shell 类工具，不能默认无限开放。

#### 后续产品路线

后续开发不再只围绕“笔记助手”增加功能，而是朝更实用的个人 AI 助手演进。当前规划了四条主线：

- **智能备忘录**：把单纯的笔记回顾扩展为待办、提醒、承诺、长期事项和复习记录统一管理的记忆中心。
- **MCP 支持**：让外部工具通过统一协议接入现有 Skill/Tool 编排体系。
- **系统字幕实时翻译**：从手动输入翻译升级为接入系统字幕或文本流，服务会议、网课和真实对话。
- **架构精简与桌面端探索**：评估从完整 Web 架构收敛为更轻量的本地桌面应用，降低日常使用摩擦。

详细路线见 [下一阶段开发路线图](./roadmap_next.md)。
